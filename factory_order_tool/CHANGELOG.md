# 更新日志

## [1.2.9] - 2026-04-26

### 适配（重要）— 生久新版 PDF「理论交期」列格式变更

**客户反馈**：
  生久 ERP 系统改版，采购单 PDF 最后一列从"交期回复"改为"理论交期"，
  内容格式变成「日期 + 版本号」两行组合（如 "2026-08-01\\nA03"）。
  用工具解析后，图纸比对界面显示"订单版本 = 2026-08-01"（日期被误当版本），
  与图纸库版本 A03/B01 等对比后全部报"不匹配"。
  客户诉求：忽略日期，只抓版本号。

**根因（双层）**：
  1. `pdf_parser._parse_main_row` 把最后一列 cell 直接 strip 存进"交期回复"字段。
     若 pdfplumber 把日期放在主行末列、版本号放在续行末列，
     `_parse_continuation` 只处理 col1（备注列），版本号被丢弃。
  2. `drawing_checker.extract_version_from_reply` 原实现是
     `return reply_text.strip()`，整串直接当版本号，无法从"日期+版本号"混合
     文本中提取版本号 token。

**修复（双管齐下，兼容两种 pdfplumber 切分行为）**：

  1. `drawing_checker.extract_version_from_reply` 智能提取版本号：
     - 逐行扫描，跳过日期行（yyyy-mm-dd / yyyy/mm/dd / yyyy.mm.dd）
     - 匹配版本号 token（字母+可选分隔符+数字，或纯字母）
     - 兜底：从整串中搜带空白边界的版本号 token（如 "REV A02" → "A02"）
     - 15 项单元测试全通过（含边界、空、None、老纯版本号回归）

  2. `pdf_parser._parse_continuation` 抓续行末列版本号：
     - 若续行末列是纯版本号 token，追加到"交期回复"字段（换行分隔）
     - 严格模式：仅匹配 `[A-Z][/.]?\\d+` 或 `[A-Z]$`，避免误吃"需求4/10"、
       "6/15"等非版本内容
     - 老 PDF 续行末列通常为空或与备注列相同，不会被误伤

**兼容性**：
  - 老 PDF（末列即版本号）：extract_version_from_reply 原样返回，行为不变
  - 新 PDF (同 cell 换行日期+版本)：智能提取跳过日期 → 版本号
  - 新 PDF (主行日期 / 续行版本)：_parse_continuation 追加，再由智能提取拆出版本

**回归覆盖**：
  - 单元测试 15/15（含 6 项新格式 + 4 项老格式 + 5 项边界/异常）
  - 端到端 4/4 场景（同 cell 换行 / 主续行分离 / 老格式主行 / 老格式伪日期干扰）
  - 久益3-30.pdf 42 项解析：项次连续、数量对账精确、交期回复无异常追加

## [1.2.8] - 2026-04-25

### Hotfix（重要）— v1.2.7 升级器编码兼容性修复

**线上反馈**：客户双击 v1.2.7 升级包内的「升级.bat」后出现一片乱码报错：
```
'鎴愮?-' 不是内部或外部命令
'wershell' 不是内部或外部命令
'升级.ps1' 找不到
```

**根因（v1.2.7 测试盲区）**：
v1.2.7 的闭环测试只用了 PowerShell 直接 `-File` 调起 ps1，**没真实模拟客户双击 .bat 的链路**。
导致两层编码 bug 漏检：
  1. 升级.bat 文件含 UTF-8 BOM (`EF BB BF`)，cmd.exe 默认按系统 ANSI（中文 Windows 上是 GBK）
     读取 bat，BOM 三字节被错误解析为非法命令，第一行就报错。
  2. bat 中调用 ps1 的命令行 `"%~dp0升级.ps1"` 含中文文件名，cmd 把这里的字节
     按 GBK 还是 UTF-8 解码取决于环境，调用 powershell.exe 时路径错乱，
     报错"找不到 升级.ps1"。

**修复**：
  1. **升级.ps1 重命名为 upgrade.ps1** —— bat 调用语句中不再出现非 ASCII 字符，
     彻底避开 cmd 代码页依赖。
  2. **升级.bat 内容全部改为 ASCII**（英文 echo / title），文件保存为无 BOM。
     - 文件名仍叫「升级.bat」（资源管理器按 Unicode 显示，对客户双击场景透明）。
     - 客户双击后短暂闪过英文进度，随即 ps1 弹窗显示中文（ps1 是 UTF-8 BOM 能正确读）。
  3. **修复 ps1 内 exclude 列表**：v1.2.7 因为 ps1 改名后忘了同步 exclude 列表，
     导致 upgrade.ps1 被错误复制到客户部署目录污染。

**新增测试规范**：
  - 升级器测试必须用 `cmd /c "升级.bat" -OldPath ... -NoLaunch` 真实模拟客户双击
  - 不允许用 `powershell -File upgrade.ps1` 跳过 bat 这一层

**升级链路总规则**（沉淀到工程约定）：
  - bat 文件：纯 ASCII 内容，无 BOM
  - ps1 文件：UTF-8 with BOM，文件名 ASCII
  - bat 引用 ps1 时不出现非 ASCII 字符
  - 文件名「升级.bat」可保留中文（Windows 资源管理器双击不依赖代码页）

## [1.2.7] - 2026-04-25

### 部署体验（无业务代码变更，仅升级链路）

**背景**：v1.2.5 的双产物方案要求客户手动把 exe + _internal\ 拖到旧目录覆盖。
   隐患：① 没有自动备份，操作失误难恢复；
        ② 旧版 _internal\ 中的废弃文件不会被清理，存在残留风险；
        ③ 客户需自行区分"代码 vs 数据"。

**改进**：升级包内置自动升级助手，整体替换式部署，干净且可回滚。

#### 新增升级助手
- 升级包结构新增三个辅助文件：
  - `升级.bat` — 客户双击入口，仅 5 行，作 PowerShell 引导
  - `升级.ps1` — 升级主逻辑，约 130 行
  - `user_data_files.txt` — 用户数据白名单（mapping_table.xlsx / settings.json）

- 客户操作流程从「拖 2 个项目覆盖」简化为「双击升级.bat」：
  1. 弹窗选择旧部署目录（FolderBrowserDialog，校验合法性）
  2. 备份旧目录到 `<旧目录名>-backup-<时间戳>\`
  3. 按白名单从备份目录把用户数据迁移到升级包
  4. 把升级包内容（排除升级辅助自身）部署到旧目录原路径
  5. 弹窗确认是否启动新版本

- 升级助手特性：
  - 整体替换式部署，避免旧版废弃 _internal 文件残留
  - 自动备份至同级目录，回滚只需改名即可恢复
  - 用户数据白名单维护在 `release/user_data_files.txt`，
    未来扩展（如新增缓存/历史目录）只加一行
  - 中文路径友好（PowerShell `-LiteralPath` + UTF-8 BOM）
  - 自我吞噬保护（拒绝把"升级包目录"当作"旧目录"）

#### 部署说明文案改写
- `release/部署说明_template.txt` 主推「双击升级.bat」
- 同时保留手动升级方式作为备选
- 增加回滚步骤说明（用 backup 目录改名即可恢复）

#### build.bat 配套改动
- 升级包内自动复制 `升级.bat` / `升级.ps1` / `user_data_files.txt`
- 末尾打包成功提示同步更新

## [1.2.6] - 2026-04-25

### 语义修复（重要 - 影响图纸比对结果可信度）

**客户反馈**：PDF 交期回复列还没填，工具就已经把"订单版本"列填上了 A01/A03 等版本号。
客户疑问"这版本号哪儿来的"——经查为本地映射表「品名规格」末尾 token，
**并非客户系统的最新版本**。

**根因**：v1.1.0 在 `drawing_checker.check_drawings` 加了一个版本号 fallback：
```python
order_version = extract_version_from_reply(row.get("_交期回复", ""))
if not order_version:
    order_version = extract_version_from_name(row.get("_产品名称", ""))
```
当用户未填交期回复列时，回退到从映射表「品名规格」末尾解析版本号。
但映射表里的版本是工厂上次维护的本地旧版本，跟客户 ERP 系统的最新版本无关。
比对时拿"本地旧版本"和"图纸库本地版本"对照——**自比必然全绿**，
伪造"已与客户最新版本比对完成"的假象，破坏客户的标准工作流：
> 第一步：从客户 ERP 查最新版本，填入 PDF 交期回复列
> 第二步：用这个版本和本地图纸做比对

**修复**：
- `drawing_checker.check_drawings` 移除 `extract_version_from_name` fallback。
  订单版本号唯一来源 = PDF 交期回复列（用户从客户系统查到后手填）。
- 未填时显式返回 `no_version` 状态，message 改为
  「请先去客户系统查最新版本号填入PDF交期回复列」。
- `main._check_drawings` 比对完成后若发现 `no_version` 项，
  弹窗列出待填 YY 编号 + 完整工作流引导。
- 状态栏文案配合修订：
  「图纸比对暂停: N 项缺订单版本号，请先去客户系统查最新版本填入 PDF 交期回复列」。

**保留 `extract_version_from_name` 函数本体**，仅移除 `check_drawings` 内的调用，
未来如需"宽容模式"开关可重新引入。

## [1.2.5] - 2026-04-25

### 鲁棒性建设（重要 - 解析层防御性补丁）

**背景**：v1.2.4 修复了「整页表格被 pdfplumber 误识别成零碎子表导致 8 项漏检」的具体场景，
但同类失败模式（部分项漏检、字段错位、列序变化等）仍可能静默发生。
v1.2.5 在解析层加入项次连续性自检 + 合计对账两条独立校验，
把「静默失败」全面转换为「显式告警」。

#### 补丁 A：项次连续性自检 + 自动二次兜底
- `pdf_parser._post_validate` 在解析完成后扫描所有项目的项次集合，
  检测 [min..max] 范围内是否有缺失。
- 若发现缺失，自动对**全 PDF 文档文本**触发 `_parse_text_fallback` 重新扫描，
  按 `(项次, YY编号)` 去重补回缺失项。
- 与 v1.2.4 的页级兜底形成两层冗余防御：
  - 页级兜底（v1.2.4）: 单页表格完全失败时触发
  - 全文兜底（v1.2.5）: 任何项次缺失时触发，可补救页级也失败的情形

#### 补丁 B：解析告警条 + 强制弹窗
- 主界面新增红/黄双色告警条：
  - **红色**: 项次彻底缺失（兜底也补不回）/ 合计对账失败 → **强制弹窗**
  - **黄色**: 兜底已自动补回 → 仅状态条提示，不打断操作
- 让用户主动感知 PDF 异常，避免基于不完整数据导出 Excel。

#### 补丁 C：合计行对账
- `pdf_parser._extract_totals` 从 PDF 末尾抓取「合计数量 / 采购总含税金额」。
- 与所有项目的实际汇总（数量、金额）做差，超过容差 `_QTY_TOLERANCE=0.5`
  / `_AMOUNT_TOLERANCE=0.05` 即触发红色告警。
- 这是**与项次自检独立的第二条校验链**，可发现「项次连续但单项数量错误」
  这类项次自检看不出的问题。

### API 变更
- `pdf_parser.parse_purchase_order` 返回值从 `(header, items)` 改为
  `(header, items, warnings)`。`warnings` 为 dict，包含项次缺失列表、
  对账数据、`has_warning` 总开关等。
- 调用方需相应调整（GUI 已配合升级）。

## [1.2.4] - 2026-04-25

### 修复（重要）
- **修复某些订单 PDF 整页项目漏检的问题**
  - 现象：当某页表格线异常导致 pdfplumber 把整页拆成多个零碎子表时，
    项次行的 YY 编号会被丢出 cell，进而整页项目从结果中消失。
    线上案例：`久益3-30.pdf` 第 5 页 8 项（项次 33-40）整段缺失，
    包括客户报告的 40 项 `YY60039328`。
  - 根因：`pdf_parser._parse_table` 严格依赖表格列结构，
    当 `extract_tables()` 返回的子表里没有合法项次列时静默丢弃整页。
  - 修复：新增 `pdf_parser._parse_text_fallback`，当某页表格路径解析出
    0 个带 YY 编号的项目、但纯文本中能匹配「项次 + YY编号」锚点行时，
    自动切换到基于 `page.extract_text()` 的逐行扫描兜底解析。
    输出字段与原有路径完全一致，下游 code_mapper / drawing_checker
    无需感知差异。
